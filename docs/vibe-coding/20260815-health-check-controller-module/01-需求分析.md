# Health Check Controller 模块化：需求分析

## 输入与产物角色

- 输入类型：`existing-requirement`
- 权威来源：用户在当前会话中确认的要求：Health Check Controller 按模块建目录；目录包含 `register.go`、`controller.go`、`types.go`、`convertor.go`；模块附带 README；Service 保有服务契约，Controller 通过构造函数注入；每层给出可由 GoMock 驱动的单元测试样例。
- 产物角色：`product-baseline` 与 `design-ready-input`
- 消费锚点：本文“产品基线 / MRD-PRD”“现有系统证据”和“流程分级”。

## 标准化需求包

- 明确功能点：将当前单文件 Health Check Controller 重组为模块目录；使 `convertor.go` 实际负责 Service 结果到 HTTP DTO 的转换；保留显式依赖注入；同步更新 GoMock 生成声明和三层测试样例；在模块 README 说明职责、依赖方向和测试策略。
- 明确约束：Service 层定义并拥有 `HealthCheckService`；Controller 不创建 Service/Manager/Probe；不保留旧 Controller 路径作为兼容层；HTTP 成功与错误响应、OpenAPI 操作和 Knife4go 文档行为保持不变；不新增框架、数据库、权限或外部依赖。
- 未获取或不确定内容：无影响验收的缺口。覆盖率仅作为发现缺口的辅助指标，不设人为百分比门槛。

## 产品基线 / MRD-PRD

- 深度：`refine`
- 行业研究决策：`skipped`；这是现有项目内部重构，已确认的本地接口、分层和测试行为足以形成验收，外部研究不会改变实现边界。
- 问题与触发场景：单文件 Controller 同时承载路由声明、HTTP 适配和固定响应，扩展时容易把接口 DTO、转换与业务调用耦合在一起，也不便展示每层如何以 Mock 隔离测试。
- 目标：把一个完整的 Health Check 示例沉淀为可复用的模块化模板，依赖方向为 `router -> controller -> service -> manager -> probe`，并让每个跨层依赖显式可替换。
- 非目标：不新增健康检查能力、不改变 URL/状态码/JSON/OpenAPI 文档、不将所有 Controller 或全项目迁移为该目录结构、不引入 UseCase 层或通用 DI 容器。
- 业务规则、权限、数据与异常：无数据写入、无鉴权变化；Service 失败仍转换为现有 `humax.InternalServerError("v1", err)` 错误包络；成功结果仍是 `data: ["success"]`。

### 可执行验收标准

1. `server/controller/health_check/` 恰含职责明确的 `register.go`、`controller.go`、`types.go`、`convertor.go` 和 `README.md`，旧 `server/controller/health_check.go` 与其测试迁移/删除，不留下兼容包装。
2. `HealthCheckService` 继续位于 `server/service`，由 Controller 的构造函数注入；Service 实现返回一个最小领域结果，Controller 不读取 Manager/Probe。
3. `convertor.go` 将该领域结果转换为现有 HTTP 成功输出，不能只保留无业务意义的空壳文件。
4. Router 只在 composition root 组装 Probe、Manager、Service、Controller，使用新模块包注册路由。
5. Controller 测试用 `MockHealthCheckService` 覆盖成功和 Service 失败；Service 测试用 `MockHealthCheckManager` 覆盖成功结果和错误包装；Manager 测试用 `MockHealthProbe` 维持成功/失败覆盖。
6. 更新 `server/mocks/generate.go` 和生成的 Mock，使 `go generate ./...` 后仓库无差异。
7. `GET /health-check` 仍返回 HTTP 200、既有四个顶层字段和 `data:["success"]`，不含 `$schema` 或 `Link`；服务失败仍为既有 500 错误包络；Knife4go 的 OpenAPI 3.0.3 文档路由不变。
8. `go test ./...`、`go test -race ./...`、`go vet ./...`、`go build ./...`、`go generate ./...` 与 `git diff --check` 全部通过。

## 现有系统证据

- 取证范围：`server/controller/health_check.go`、其测试、`server/router/router.go` 与其测试、`server/service/health_check.go` 和 `server/service/health_check/*`、`server/manager/health_check*`、`server/mocks/generate.go`、`common/humax`；未读取无关业务模块。
- 项目事实：目标仓库为 `F:/baidu/aiib-go/generate-example-project`；Go 1.25，Gin + Huma v2.39.1；GoMock v0.6.0 已作为直接依赖；真实生成命令是 `go generate ./...`。
- 功能入口与代表路径：`server/router/router.go` 在 `newHealthCheckController` 中组装 `LocalProbe -> Manager -> Service -> Controller` 并由 `registerRootAPI` 注册。当前 Controller 调用 `service.Check(context.Context) error` 后直接返回 `humax.Success("v1", []string{"success"})`。
- 现有测试模式：Controller 以 `httptest` + `MockHealthCheckService` 断言 HTTP 包络；Service 以 `MockHealthCheckManager` 断言错误包装；Router 测试冻结 HTTP 字段、`$schema`、`Link` 与 Knife4go 文档行为。
- 生成物边界：`server/mocks/generate.go` 是唯一手写生成声明；`server/mocks/mock_*.go` 是 `mockgen` 产物，不手工编辑。
- 重要兼容事实：Huma 的 Docs/OpenAPI/Schemas 内建路径已特意关闭，`CreateHooks=nil` 用于避免在旧响应中加入 `$schema`/`Link`；本需求不改动这些设置。

## 范围与影响

- 范围：`backend`
- 影响模块：Controller 模块包、Router 导入与 composition root、Service 结果契约与实现测试、Mock 声明/产物、项目内模块 README。
- 对用户行为：无变化；这是代码结构与可测试性的改善。

## 低风险实现假设

- `HealthCheckResult{Status string}` 足以表达本 demo 的业务结果；Service 在 Manager 成功后返回 `Status: "success"`，由 Controller convertor 映射为单元素 `[]string`。验证方式：Service/Controller/Router 的自动化测试共同断言该路径。
- `HealthCheckController` 接口随模块迁移至 `server/controller/health_check`，Mock 生成器同步改为该包；因为调用方仅 Router 和测试，且本次明确不需要旧包路径兼容。验证方式：全仓编译和 `go generate ./...`。
